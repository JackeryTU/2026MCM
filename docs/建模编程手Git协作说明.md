# 建模手／编程手 GitHub 协作说明

## 只需记住

```text
队长第一次发布：01_队长首次发布项目.cmd
非队长第一次加入：02_队员首次下载项目.cmd
每次开始工作：04_获取队友最新文件.cmd
每次完成一小块：03_上传我的修改.cmd
```

建模手和编程手可以是同一人，不需要建立角色分支。主要维护模型分析、代码、`results/` 和 `figures/`；正式论文由论文手在 `paper/` 中维护。

## 如果你是队长：第一次发布

整个项目只运行一次 `01_队长首次发布项目.cmd`：

1. 安装 Git for Windows：<https://git-scm.com/download/win>。
2. 确认目标私有仓库是 <https://github.com/JackeryTU/2026MCM>。
3. 双击 `01_队长首次发布项目.cmd`，根据中文提示输入 `Y`。
4. 输入自己的 GitHub 用户名和邮箱。
5. 按浏览器提示完成 GitHub 登录。
6. 出现“[完成]”后，在仓库的 `Settings → Collaborators` 中邀请两名队员。
7. 把 `02_队员首次下载项目.cmd` 单独发给队员。

发布成功后不再运行“01_队长首次发布项目”，日常只使用“04_获取队友最新文件”和“03_上传我的修改”。

## 如果你不是队长：第一次加入

1. 安装 Git，并接受 GitHub 私有仓库邀请。
2. 新建一个空的父文件夹，例如 `D:\MathModel`。
3. 把 `02_队员首次下载项目.cmd` 放进去并双击。
4. 根据中文提示输入 `Y`，登录收到邀请的账号。
5. 输入自己的 GitHub 用户名和邮箱。
6. 出现“[完成]”后，只在新生成的 `2026MCM` 文件夹中工作。

## 每次建模或编程的标准流程

1. 在群里认领准备修改的问题和文件。
2. 双击 `04_获取队友最新文件.cmd`。
3. 修改模型分析、术语表、求解程序、结果或图片。
4. 实际运行代码，确认结果可复现。
5. 检查 `results/`、`figures/` 和模型说明是否一致。
6. 如果变化会影响论文，在 `reviews/论文修改意见.md` 登记一条“必改”意见。
7. 双击 `03_上传我的修改.cmd`。
8. 检查脚本列出的全部文件，确认后输入 `Y`。
9. 输入提交说明，例如 `code: 完成问题二求解`。
10. 出现“[完成]”后，在群里通知论文手和其他成员。

建议每得到一问的可运行结果就上传，不要等全部问题完成后一次上传。

## 模型调整会影响论文时

不要根据自己电脑中的旧论文直接修改 `paper/`。建模手负责把变化说清楚，论文手负责改正式论文。

建模手应当：

1. 更新模型分析、代码、`results/` 和 `figures/`。
2. 重新运行并验证结果。
3. 在 `reviews/论文修改意见.md` 中写明：
   - 模型为什么调整；
   - 新旧模型有什么差异；
   - 论文中的哪些公式、参数、表格、图片或结论受影响；
   - 权威代码、结果和图片分别在哪里。
4. 运行 `03_上传我的修改.cmd`。
5. 在群里通知论文手，并给出对应意见 ID。

论文手处理后会把状态改为 `已处理待复核`。建模手或审查人应检查论文是否与新版模型一致，确认后改为 `已关闭`。

## 上传时发现论文手已经更新

不会用你的旧论文覆盖新论文。只要你没有修改 `paper/`，你的提交中就不包含论文文件。

按以下顺序操作：

```text
运行“03_上传我的修改”保存模型修改，但提示 GitHub 已更新
→ 运行“04_获取队友最新文件”，获取论文手的新论文
→ 再运行“03_上传我的修改”，上传尚未推送的模型版本
```

第二次运行“03_上传我的修改”时，即使没有新的文件修改，它也会找到并上传之前保存的版本。

## 常见问题

### “04_获取队友最新文件”会覆盖没做完的代码吗？

不会。本地存在未提交修改时，获取脚本会停止。先运行“03_上传我的修改”保存修改，再运行“04_获取队友最新文件”。

### 代码还不能运行，可以上传吗？

原则上不要把无法运行的状态当成正式结果上传。如果为了防止丢失必须保存，提交说明要明确写 `WIP: 问题二代码未完成`，并立即在群里提醒其他成员不要引用其结果。

### 纯代码整理需要通知论文手吗？

如果公式、参数、数值、图片和结论完全不变，只需在提交说明和群消息中说明。如果任何论文内容可能变化，必须登记论文修改意见。

### 本地论文是旧版，会不会覆盖 GitHub 的新版论文？

不会，前提是没有修改 `paper/`。运行“03_上传我的修改”时如果列表中意外出现论文文件，应取消上传并联系论文手。

### 两个人修改同一段代码怎么办？

修改前先认领文件。同一文件的不同位置可能自动整合，同一位置可能冲突。出现 `conflict` 或 `rebase failed` 时停止操作，由相关成员一起处理。

### CSV、Excel、图片能自动合并吗？

不要依赖自动合并。尤其是 Excel、PDF、图片和压缩包，同一时刻只让一个人维护。CSV 即使是文本，也应避免两个人同时生成同一个结果文件。

### data 中的原始附件可以修改吗？

不可以。`data/` 中的题目附件和原始数据只读。清洗或派生数据应由程序生成到约定的结果位置，不覆盖原始附件。

### 大数据文件可以直接上传吗？

先让队长确认文件大小和方案。较大文件可能需要 Git LFS，或者只在 README 中记录获取方式。不要个人随意修改 `.gitignore`。

### 网络中断后修改会丢吗？

不会。已提交的修改保留在本机，网络恢复后重新运行“03_上传我的修改”；获取失败也不会删除现有文件。

### “03_上传我的修改”中的 M、??、D 是什么意思？

- `M`：文件被修改；
- `??`：新增文件；
- `D`：文件被删除。

看到意外的 `D`、`paper/` 或无关文件时，取消上传并联系队长。

## 必须停止并找队长的情况

- 出现 `conflict` 或 `rebase failed`；
- 不确定结果是否可以作为论文依据；
- 误改了 `paper/` 或其他人负责的文件；
- 准备上传超大文件；
- 脚本显示的仓库地址不对；
- 出现其他看不懂的失败信息。

不要自行运行 `git push --force`、`git reset --hard`、`git clean` 或 `git checkout -- 文件名`。

## 最后速查

```text
队长第一次：01_队长首次发布项目
非队长第一次：02_队员首次下载项目
开始建模或编程：04_获取队友最新文件
完成可运行的小版本：03_上传我的修改
影响论文：登记 reviews → 上传修改 → 通知论文手
远程已更新：获取最新文件 → 上传修改
发生冲突：停止并找队长
```
