# 建模手／编程手快速开始

这份说明写给第一次使用 Git 和 GitHub 的建模手／编程手。你不需要理解 Git，也不需要输入命令，按自己的身份选择路线并双击脚本即可。

团队已经建好私有 GitHub 仓库，也已经发出成员邀请。建模手与编程手可以是同一人，主要维护模型分析、代码、`results/` 和 `figures/`；正式论文由论文手维护 `paper/`。

## 一、你的职责与硬性约束

### 你负责什么

- 建模分析：维护 `题目分析报告.md` 和 `术语表格.md`，写清假设、变量、约束、公式、算法和评价方法。
- 编程实现：维护各问求解代码，实际运行程序并检查结果。
- 结果交付：维护 `results/` 中的权威数值结果和复现信息。
- 图表交付：维护根目录 `figures/` 中由数据和代码产生的权威候选图。
- 论文交接：模型、参数、结果或图片变化会影响论文时，在 `reviews/过程归档/03_论文核查与渲染/论文修改意见.md` 登记并通知论文手。
- 论文复核：论文手处理模型更新后，检查公式、参数、数值、图片和结论是否一致，再关闭意见。

### 你不能做什么

- 不修改 `data/` 中的题目附件和原始数据；原始输入始终只读。
- 不编造运行结果，不手工修改结果来迎合预期结论，不把未运行代码描述为已经验证。
- 不把无法复现、来源不明或尚未核验的数值交给论文手作为正式结论。
- 不因为自己电脑中的 `paper/` 是旧版，就用它覆盖 GitHub 上论文手的新版本。
- 原则上不直接修改 `paper/`；确需共同修改时，必须先取得论文手同意并明确认领文件。
- 不用 Skill 生成的参考初稿替换正式论文，不把 `参考初稿.pdf` 放入最终提交目录。
- 未经沟通，不修改其他成员正在维护的同一文件；不随意删除文件或调整 `.gitignore`。

### 每次交付前必须做到

1. 开始前在群里说明准备修改的问题和文件。
2. 开始工作前运行 04，完成一个可说明的小版本后运行 03。
3. 实际运行代码，确认无报错，并记录关键参数、随机种子、依赖和复现方法。
4. 确认模型说明、代码、`results/` 和 `figures/` 相互一致。
5. 未完成但必须备份的代码，提交说明以 `WIP:` 开头，并在群里提醒“结果暂不可引用”。
6. 任何会改变论文公式、参数、表格、图片或结论的更新，都必须登记修改意见并通知论文手。
7. 检查上传列表；意外出现 `paper/` 或其他人负责的文件时，取消上传并先沟通。

### 如果你兼任队长

- 只有你可以运行一次 `01_队长首次发布项目.cmd`，成功后不得重复运行。
- 确认两名队员接受邀请，并等首次发布完成后再通知他们运行 02。
- 维护 README 中的当前分工，协调同一文件的占用，处理成员遇到的冲突和权限问题。
- 不要求队员使用强制推送、强制重置或删除本地修改来解决问题。
- 最终提交前组织核对官方规则、正式论文、附件和 `submission/`，不能把参考初稿误作正式文件。

## 二、所有人先安装 Git

1. 打开 <https://git-scm.com/download/win>。
2. 下载并运行 Git for Windows 安装程序。
3. 保持默认选项，一直点击 Next，最后点击 Install。
4. 安装完成后关闭安装程序。

如果此前打开过脚本窗口，请先关闭，再重新双击脚本。

## 三、第一次使用：根据身份二选一

### 路线 A：你是队长，项目模板还没有发布

只有队长执行，而且整个团队只执行一次。

开始前确认：

- 私有仓库地址是 <https://github.com/JackeryTU/2026MCM>；
- GitHub 仓库还没有 main 分支或项目文件；
- 当前模板文件夹中有四个 cmd 脚本和项目模板；
- 两名队员已经收到仓库邀请。

操作步骤：

1. 打开本机项目模板文件夹。
2. 双击 `01_队长首次发布项目.cmd`。
3. 看到确认提示后输入 Y，按回车。
4. 按提示输入自己的 GitHub 用户名和邮箱。
5. 如果浏览器弹出 GitHub 登录页面，登录仓库所有者账号并授权。
6. 等待窗口显示“[完成]”。
7. 打开 GitHub 仓库网页，刷新并确认能看到项目文件。
8. 提醒两名队员接受邀请。
9. 把 `02_队员首次下载项目.cmd` 单独发给两名队员。

发布成功后不要再次运行 01。队长以后也只使用 04 和 03。

### 路线 B：你不是首次发布项目的队长

1. 登录被邀请的 GitHub 账号。
2. 接受邀请，并确认能看到私有仓库。
3. 等队长明确通知“项目已经首次发布”。
4. 在电脑上新建空文件夹，例如 `D:\数学建模比赛`。
5. 把 `02_队员首次下载项目.cmd` 放入空文件夹。
6. 双击脚本，输入 Y，按回车。
7. 如果浏览器弹出登录页面，登录已接受邀请的账号并授权。
8. 按提示输入自己的 GitHub 用户名和邮箱。
9. 等待窗口显示“[完成]”。

脚本旁边会出现新的 `2026MCM` 文件夹。以后只在这里工作，不再运行 02。

不要从 GitHub 页面下载 ZIP。后续协作必须使用脚本下载的项目文件夹。

## 四、确认第一次准备完成

工作文件夹中应该至少能看到：

    data/
    results/
    figures/
    paper/
    reviews/
    03_上传我的修改.cmd
    04_获取队友最新文件.cmd

队长使用首次发布的原文件夹；其他成员使用脚本新建的 2026MCM 文件夹。三个人不要通过网盘共同编辑同一个物理文件夹。

## 五、以后每次建模或编程

固定顺序：

    获取队友最新文件 → 修改 → 实际运行并检查 → 上传我的修改

具体操作：

1. 打开自己的项目文件夹。
2. 在群里说明准备修改的问题和文件。
3. 双击 `04_获取队友最新文件.cmd`。
4. 看到“[完成]”后再开始工作。
5. 修改自己负责的文件，例如：
   - `题目分析报告.md`；
   - `术语表格.md`；
   - `问题X_求解.py` 或 MATLAB 文件；
   - `results/`；
   - `figures/`。
6. 实际运行代码，确认结果可以复现，模型说明、结果和图片一致。
7. 如果变化会影响论文，在 `reviews/过程归档/03_论文核查与渲染/论文修改意见.md` 登记“[必改]”意见。
8. 双击 `03_上传我的修改.cmd`。
9. 检查窗口列出的文件。确认都是本次修改后输入 Y。
10. 输入修改说明，例如：`code: 完成问题二求解`。
11. 看到“[完成]”后，在群里通知论文手和其他成员。

建议每得到一问的可运行结果就上传，不要等全部问题完成后才上传。

## 六、模型变化会影响论文时

不要根据自己电脑中的旧论文直接修改 paper。正确流程是：

1. 更新模型分析、代码、results 和 figures。
2. 重新运行并验证结果。
3. 在 `reviews/过程归档/03_论文核查与渲染/论文修改意见.md` 写清调整原因、变化内容、论文受影响位置，以及最新代码、结果和图片的位置。
4. 运行 `03_上传我的修改.cmd`。
5. 在群里通知论文手并给出意见编号。

论文手修改正式论文后会标记“已处理待复核”。建模手检查论文与新模型一致后，再把意见改为“已关闭”。

## 七、脚本提示失败怎么办

### 获取时提示本机还有修改

先运行 03 保存修改，再运行 04 获取更新。

### 上传时提示队友已经先上传更新

你的修改已经安全保存在电脑中。运行 04，成功后再运行 03。第二次运行 03 时，即使没有新的文件变化，也会继续上传此前保存的版本。

### 上传列表中意外出现 paper 文件

不要输入 Y，直接取消。联系论文手和队长，确认是否误改了正式论文。

### 出现 conflict、rebase failed 或看不懂的报错

立即停止，不要继续尝试命令。保留窗口，把完整截图发给队长。

不要自行使用 force push、reset --hard、git clean 或 checkout 撤销文件。

## 八、最后速查

    队长第一次：安装 Git → 运行 01
    其他成员第一次：安装 Git → 接受邀请 → 等队长发布 → 运行 02
    每天开始：运行 04
    工作位置：模型说明、代码、results/、figures/
    完成可运行的小版本：运行 03
    影响论文：登记 reviews → 运行 03 → 通知论文手
    出现冲突：停止并找队长

更完整的规则见 [建模手／编程手 Git 协作说明](建模编程手Git协作说明.md)。
