# 数学建模比赛共享工作区

本仓库用于 3–4 天数学建模比赛中的建模、编程、论文写作、审查和提交协作。

## 竞赛信息

- 竞赛名称：2026 年全国大学生数学建模竞赛
- 竞赛届次：2026 年
- 题目编号：C
- 可选题范围：A、B、C 题中任选一题
- 竞赛时间：2026-09-10 18:00 至 2026-09-13 20:00
- 校内安排来源：`赛前准备.pdf`，2026-08-08
- 校内详细时间线：见 `docs/2026国赛校内安排.md`

在开始正式论文排版前，必须以当届官方规则和官方模板核验匿名要求、页数、文件名、文件大小及提交方式。

## 文件结构与职责

先按下面的结构找文件。根目录放建模与编程的主要产物；论文、审查意见、协作资料和最终提交文件分别进入各自工作区。

```text
共享工作目录/
├── 使用指南.md                    Skill 产物的使用边界与人工核验要求
├── data/                         题目和官方附件（只读）
├── 题目分析报告.md                建模方案与分析
├── 术语表格.md                    全队统一的术语、符号和单位
├── 问题X_求解.py / .m             各子问题的求解及绘图主代码
├── utils/                        绘图样式与出版级导出辅助工具
├── results/                      程序产生的权威数值结果
├── figures/                      程序产生的候选图、预览与图表面板
│   └── _qa/                      自动生成的灰度质检预览（出现时保留）
│
├── paper/                        论文手实际撰写的正式论文工程
├── reviews/
│   └── 论文修改意见.md             当前论文的审查与变更通知
│
├── 参考初稿-LaTeX/                Skill 生成的参考源码（可能尚未生成）
├── 参考初稿.pdf                   Skill 生成的参考 PDF（可能尚未生成）
├── 参考初稿.build.json            参考 PDF 的构建记录（可能尚未生成）
│
├── docs/                         协作说明、规则和赛前参考资料
├── submission/                   最终冻结文件与提交检查
└── 01/02/03/04_*.cmd             Git 协作脚本
```

### 1. 建模与编程区

主要由建模手／编程手维护。

| 位置 | 放什么 | 关键规则 |
|---|---|---|
| `使用指南.md` | Skill 定位、交付边界和人工核验要求 | 使用 Skill 前必读；Skill 产物均须由团队核验 |
| `data/` | 官方题目、数据附件和模板原始包 | 原始文件只读；大文件的获取方法和哈希写入 README |
| `题目分析报告.md` | 问题分析、模型方案和算法设计 | 模型发生实质变化时同步更新 |
| `术语表格.md` | 术语、符号、单位和中英文名称 | 全队统一采用，论文手不得另造冲突定义 |
| `问题X_求解.py` / `.m` | 各子问题的数据处理、模型求解、验证和绘图主代码 | 每问一个主文件；修改图片必须改代码后重跑，不能直接修改位图 |
| `utils/` | 从 Skill 复制的绘图样式和出版级导出工具 | Python 使用 `plot_style.py`；MATLAB 使用 `apply_publication_style.m`、`audit_publication_figure.m`、`export_publication_figure.m`；只放复用工具，不放生成图片 |
| `results/` | CSV、XLSX 和 `复现清单.json` 等真实运行结果 | 是论文数值的权威来源，不手工修改程序生成的数据 |
| `figures/` | SVG、至少 300 DPI PNG、灰度预览及可选的 `图表面板.html` | 是候选图的权威来源，按 `raw_qX_*`、`process_qX_*`、`result_qX_*` 命名 |

`data/README.md`、`utils/README.md`、`results/README.md` 和 `figures/README.md` 是各目录的存放说明，不是新的比赛交付物。

#### 画图文件放置规则

不要把“绘图代码”“生成的图”和“论文采用的图”混在一起：

1. 每问的绘图主逻辑写在根目录对应的 `问题X_求解.py` 或 `.m` 中，与数据处理和模型求解保持可复现关系。
2. 多问共用的样式、配色和导出函数放入 `utils/`。
3. 代码生成的全部候选图统一输出到根目录 `figures/`，每张正式候选图同时保存 SVG 与至少 300 DPI PNG；自动生成的灰度质检预览可集中保存在 `figures/_qa/`。
4. 图片按子问题和证据类型命名：`raw_q1_*`、`process_q1_*`、`result_q1_*`，其余问题依次使用 `q2`、`q3`。
5. 论文手从 `figures/` 选择已核验图片，复制到 `paper/` 中官方模板约定的图片目录；不要使用指向根目录的软链接。
6. 图片需要调整时回到绘图代码修改并重新导出，不直接用图片编辑器修改 PNG。

Skill 对数学建模候选图的最低要求是：原始数据图、模型过程图、最终结果图每类至少 3 张，合计至少 9 张；每个子问题在三类中各至少有 1 张。同一内容的 SVG、PNG 和灰度预览只算 1 张逻辑图。

### 2. 正式论文与审查区

| 位置 | 负责人 | 关键规则 |
|---|---|---|
| `paper/` | 论文手 | 正式论文的唯一权威来源；使用当届官方 LaTeX 模板，不强制分章节 |
| `reviews/论文修改意见.md` | 审查人提出、论文手处理 | 登记必改项、跨文件问题、争议项，以及模型或结果变化对论文的影响 |

论文采用的数值必须来自 `results/`，采用的图片必须来自 `figures/`。论文手将定稿图片复制到官方模板约定的位置，不使用依赖本机路径的软链接。

### 3. 参考稿

以下三个产物由 Skill 在需要时生成，当前不存在也属于正常情况：

- `参考初稿-LaTeX/`
- `参考初稿.pdf`
- `参考初稿.build.json`

它们只供论文手参考。正式论文仍由论文手在 `paper/` 中自行撰写，禁止把 `参考初稿.pdf` 当作参赛 PDF，或用参考工程整体覆盖 `paper/`。

### 4. 资料与最终提交区

| 位置 | 用途 | 关键规则 |
|---|---|---|
| `docs/notes.md` | 长期有效的写作、格式和协作约定 | 不记录针对某一稿的临时修改意见 |
| `docs/2026国赛校内安排.md` | 本届校内时间线和提交要求 | 与全国官方规则分开记录，冲突项必须确认 |
| `docs/模板/` | 角色、题型和 LaTeX 参考资料 | 按需查阅，范例不能代替本题分析和真实结果 |
| `docs/*快速开始.md` | 零基础成员首次加入项目的操作说明 | 按自己的角色阅读 |
| `docs/*Git协作说明.md` | Git 日常操作和常见问题 | 遇到异常时查阅或联系队长 |
| `submission/` | 最终论文 PDF、支撑材料及提交记录 | 只放从 `paper/` 编译并核验后的冻结文件，不在这里修改正文 |
| `submission/提交检查清单.md` | 最终检查、哈希、来源 commit 和回执记录 | 提交前逐项填写并保留 |


## 权威来源

发生不一致时，按以下规则处理：

1. 数值、参数和指标以实际代码运行结果及 `results/` 为准。
2. 候选图片以根目录 `figures/` 为准；论文采用的图片复制到 `paper/` 的模板约定位置。
3. 正式论文文字和排版以 `paper/` 为准。
4. `参考初稿-*` 仅提供写作参考，不得覆盖 `paper/`。
5. 最终参赛文件只能由已核验的 `paper/` 工程编译并放入 `submission/`。

## 日常 Git 规则

- 全员默认使用 `main`，不设置长期角色分支。
- 修改同一文件前先在线下或群内同步。
- 小步高频提交；运行上传脚本前检查它列出的全部改动。
- 每次开始工作先运行获取脚本，完成一小块工作后再运行上传脚本。
- 大改动需要集中审查时，可临时建立短期分支并开 PR，合并后删除。

推荐提交前缀：

```text
model: 建模分析
code: 代码实现
result: 数值结果
figure: 图表更新
paper: 正式论文
review: 审查意见
docs: 规范与说明
submit: 冻结提交版本
fix: 错误修复
```

## 零基础成员使用脚本

仓库地址：<https://github.com/JackeryTU/2026MCM>（Private）。队长须先在 GitHub 仓库的 Settings → Collaborators 中邀请另外两名成员；每台电脑须安装 Git for Windows，并使用获邀的 GitHub 账号登录。

第一次使用 Git 时，请先按角色阅读快速开始：

- [论文手快速开始](docs/论文手快速开始.md)
- [建模手／编程手快速开始](docs/建模编程手快速开始.md)

熟悉基本操作后，如需查看完整规则和常见问题，再阅读：

- [论文手 Git 协作说明](docs/论文手Git协作说明.md)
- [建模手／编程手 Git 协作说明](docs/建模编程手Git协作说明.md)

四个脚本严格分工，不要混用：

| 脚本 | 谁使用 | 什么时候使用 | 会做什么 |
|---|---|---|---|
| `01_队长首次发布项目.cmd` | 仅队长 | 整个项目仅一次 | 检查远程当前文件后初始化并推送；远程当前有文件时拒绝；若仅有创建／删除 README 的历史但当前为空，则保留历史并发布本地模板；首次推送中断时可安全重试 |
| `02_队员首次下载项目.cmd` | 两名队员 | 每台电脑仅一次 | 将私有仓库的 `main` 下载到脚本旁的新 `2026MCM` 文件夹，并配置该队员身份 |
| `03_上传我的修改.cmd` | 全员 | 完成一小块工作后 | 预览、提交并推送本地修改；不会下载队友文件；远程领先时保存本地版本后停止 |
| `04_获取队友最新文件.cmd` | 全员 | 每次开始工作前 | 工作区干净时拉取 GitHub 最新版本；不会提交或上传，也不会覆盖未保存的本地修改 |

推荐日常顺序：开始工作先运行 `04_获取队友最新文件.cmd`，修改并检查文件，完成后运行 `03_上传我的修改.cmd`。若上传脚本提示队友已有新内容，先运行“04_获取队友最新文件”，再重新运行“03_上传我的修改”。脚本报告冲突时立即停止并联系队长共同处理，禁止使用 `force push` 或 `reset --hard`。

论文已经更新后若模型或结果发生变化，建模手只更新建模权威文件，并在 `reviews/论文修改意见.md` 登记影响；论文手获取更新后负责修改正式 `paper/`。建模手未修改的旧论文不会覆盖 GitHub 上的新论文。

首次 GitHub 身份验证通常会打开浏览器，选择有该私有仓库权限的账号并授权即可。脚本不会索取或保存 GitHub 密码、Token。四个脚本的文件名和操作提示均使用中文；为兼容 Windows `cmd.exe` 的中文交互，脚本使用 GBK 编码并切换到代码页 936。请直接传输和运行 `.cmd` 文件，不要把脚本文本复制到聊天窗口或网页后再另存。

如果 `03` 或 `04` 提示当前不在 `main`、仓库地址不符，或者上一次变基/合并尚未完成，应立即停止并把完整窗口截图发给队长，不要自行强制推送、强制重置或删除 `.git`。
